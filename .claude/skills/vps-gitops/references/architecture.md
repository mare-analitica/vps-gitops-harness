# Reference architecture

A single VPS (typically 2–4 vCPU, 8–16 GB RAM) running a one-node Docker Swarm.
One server per client: no data or credentials are shared between clients.

## Source of truth

| What | Where | Versioned |
|---|---|---|
| Stack definitions | `setup/docker/<stack>-stack.yml` | Yes |
| Per-stack logic (derived variables, secrets, databases) | `setup/docker/hooks/<stack>.sh` | Yes |
| Client configuration (domain, feature flags, versions) — **no secrets** | `clients/<client>/config.env` | Yes |
| CI jobs for the client's apps | `clients/<client>/ci-jobs.yaml` | Yes |
| Host-specific values (client name, admin CIDRs) | `/etc/<platform>/host.env` (generated by config management) | No |
| Infrastructure secrets | `/etc/<platform>/secrets/<name>` (root, 0600) → Docker Secrets | No |
| Application secrets | Secrets vault, one versioned path per app | No (vault) |
| Host configuration | Config management roles (e.g. Ansible) | Roles yes, inventory no |

There is **no `.env` file on the server**. Configuration is layered in this
order (last wins): client config → host env → stack hook.

## Stacks

| Stack | Responsibility |
|---|---|
| `platform` | Reverse proxy with automatic TLS (via a read-only Docker socket proxy), local image registry, shared datastores (PostgreSQL, Redis, MongoDB, RabbitMQ) |
| `identity` | SSO provider (realm, groups, 2FA) and forward-auth proxies protecting admin panels |
| `vault` | Secrets vault: versioned key/value for apps, OIDC login for people, JWT login for the deploy service account |
| `ci` | CI server configured as code, building through a rootless BuildKit daemon — **no access to the host Docker API** |
| `apps-<client>` | The client's own applications; image and env arrive through the deploy queue |
| Product stacks (CRM, ERP, automation) | Vendor or open-source products, isolated on their own networks when they bring their own datastores |

Deployment order matters: `platform` → `identity` → `vault` → `ci` → apps and
products. Each depends on the previous one being healthy (database for SSO,
SSO for vault login, vault for app env).

## Stack rules

- Images pinned as `tag@sha256:<digest>`. A floating tag is an unplanned
  upgrade waiting to happen.
- `update_config.failure_action: rollback` on every service.
- **stop-first** for anything with a data volume; start-first for stateless
  services.
- Variables without defaults; the deploy queue refuses to deploy when one is
  empty (Swarm silently renders missing variables as empty strings).
- Secrets as files (`*_FILE` or a mounted Docker Secret), never in
  `environment`, so they do not show up in `docker inspect`.
- Swarm Configs and Secrets are immutable: name them with a content hash or a
  version suffix so a change produces a new object.

## Isolation per application

| Shared service | Isolation | Notes |
|---|---|---|
| PostgreSQL | Role + database per app, never the superuser | Password piped via stdin, reapplied on every deploy |
| MongoDB | User with `readWrite` on its own database only | Verify the user cannot read the admin database |
| RabbitMQ | Vhost + user per app | Fixed hostname for the broker service (see troubleshooting) |
| Redis | **Not shareable safely** | Redis ACLs cannot isolate logical databases; if the platform Redis holds SSO sessions, an app with its password could read admin sessions. Give each app that needs Redis a small dedicated instance on a private network |

## Networks

- `public_net`: reverse proxy ↔ services exposed to the internet.
- `internal_net`: shared datastores. Not reachable from the internet.
- Per-stack private overlay networks for anything that must not be reachable
  from other stacks (vendor databases, dedicated Redis).
- Service short names become DNS aliases on **every** network the service
  joins. Two stacks with a `redis` service on the same network will collide:
  prefix names or use a private network.

## Edge and access

- TLS certificates via HTTP-01 per hostname. Wildcards need DNS-01 and a DNS
  provider API that is actually available to the account.
- Admin panels are protected by either an IP allowlist or SSO forward-auth.
  SSO is preferred for teams without fixed IPs; the allowlist is kept as an
  emergency path.
- A product's first-run setup page (e.g. "create the first administrator")
  must stay behind the allowlist until the admin exists: whoever opens it first
  becomes the administrator.

## Deploy paths

| Change | Path |
|---|---|
| Stack definition, hook, platform service | `git pull` on the server → `deploy-queue stack <name>` |
| New application version | CI job → `deploy-queue app <service> <registry>/<image>@sha256:<digest> [--env <vault-path>]` |
| Host configuration | Config management run from the operator's machine |

Details: `deploy-queue.md` and `ci-pipeline.md`.
